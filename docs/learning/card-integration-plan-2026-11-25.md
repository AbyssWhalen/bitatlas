## 2. 本机并入方法与版本规则

### 2.1 追加 TSV，同时保留逐卡依据

现有 `content/learning/cards.tsv` 是四列 `id / concept / front / back`，首行以 `#` 开头。草稿六列是 `id / concept / front / back / sourceQuestionIds / doubts`，首行不是注释。不能将草稿原文件直接拼到正式源：它含表头、四行空背面候选，且现有生成器只取前四列。

建议兼容扩展正式源为 `id / concept / front / back / version / sourceQuestionIds`：保留旧 80 行的原四列，按草稿顺序追加 76 行，显式填新卡版本和英文逗号分隔的依据题。`doubts` 留在草稿与审核文档中，不混进卡片正文。生成器对原有 80 个 ID 保留旧四列行为；新增 ID 必须有版本和非空显式来源，不允许缺字段时静默走旧来源兜底。也可采用独立 ID→版本/来源元数据表，关键是这些值必须来自确定性编辑源，不能依赖上一份生成的 `learning.json`。

**来源选择需要修正。** `build-learning.mjs:36–41` 当前会找同概念全部映射，按年份保留当年最后一题，再选前四年；它不会读取草稿的 `sourceQuestionIds`。只读模拟发现，11 张新卡会因此漏掉至少一条实际采用的依据题：

`card-ds-23`、`card-ds-33`、`card-ds-35`、`card-co-22`、`card-co-28`、`card-co-29`、`card-co-30`、`card-os-32`、`card-os-34`、`card-cn-40`、`card-cn-41`。

例如 `card-ds-23` 依据 2018 Q41，旧算法却选 2010 Q42、2011 Q42、2013 Q41、2016 Q43。新卡应按显式依据题 ID 取相应 mapping 的完整 `source`（题面版本、原文档 SHA、页码、locator），验证题目和概念匹配。保留旧卡原来的来源对象，不借此批量重写旧卡。

## 4. 服务器实际分发与激活路径

### 4.1 为什么不随应用包

`apps/web/vite.config.ts:12` 在 server 模式使用 `publicDir: false`；`tools/verification/package-server.mjs:22,29` 只收应用白名单，并拒绝路径含 `content` 的文件。`apps/server/src/app.ts:36–40` 还阻止静态内容目录与 `/content/` 回退。题包、学习包和 PDF 均不属于匿名应用壳。`docs/server/release-plan-2026-11-25.md:37` 也明确“GCP 包内没有题包或学习包，不执行内容发布”。

因此，即使完成 `build:server`、打包、切换 release，生产学习包也不会改变。GitHub Pages 的本地模式会随 `public/` 发布学习 JSON，是另一条已存在的公开分发路径；推送不能替代生产内容发布，回退这两条路径时也要分别处理。

### 4.2 精确操作顺序（供组长后续执行，本轮未联网）

1. 本机候选通过本方案门禁，保留旧学习包原 JSON、旧包版本/规范摘要、候选版本/摘要和文件字节摘要。上线前由组长核对生产 `/api/v1/content` 实际版本，不假定它必然等于本机旧包；若不同，先按真实基线重做差异和兼容核对。按部署手册准备一致数据库备份与可用回退候选，不恢复或覆盖数据库。
2. 登录现有管理员账号，打开 `/settings` → “账号与同步” → “管理员：邀请与题包发布”。无需重新 bootstrap 管理员、重传 17 年题包/PDF、创建隧道或重启服务。
3. 在“预检题包或学习包”选择本机 `apps/web/public/content/learning.json`。`AccountTools.tsx:84–90` 识别 `content.id === 'bitatlas-learning'`，发送 `POST /api/v1/admin/content/preview`，JSON 为 `{ kind: 'learning', content: <完整学习包> }`。这一步只校验，不写入待发布版本。
4. 核对返回的版本、digest、`summary.cards=156`、`articles=20`、`mappings=799`、`unavailableMappings=[]`、`blockers=[]`。后端会校验学习包 schema/摘要/内部来源引用，再与**生产当前已发布题面版本**逐题对照。16 MiB 是此 JSON 接口上限；学习包不走 PDF 的分块上传接口。
5. 点击“发布已预检内容”，发送 `POST /api/v1/admin/content/publish`，JSON 为 `{ kind: 'learning', content: <同一完整学习包>, expectedDigest: <预检返回 digest> }`。需管理员会话与合法同源 Origin；普通成员不能发布。
6. `ContentService.routes` 在一个 SQLite 事务中再次预检：摘要必须相同、blockers 必须为空；同版本不同摘要报 `VERSION_CONFLICT`，版本下降报 `CONTENT_DOWNGRADE`。随后将同 ID 旧版本 `published=0`，插入新 `(id,version)` 的完整 payload 并置 `published=1`。`content_versions` 的唯一索引保证同 ID 只有一个活动版本；旧 payload 保留，不删除用户 `entities` 或事件。
7. 发布返回 `{id,version,digest}`。鉴权 `GET /api/v1/content` 确认目录切换，再 `GET /api/v1/content/bitatlas-learning` 回读完整包，验证规范摘要与 156 卡。匿名读取应仍被拒绝。后台内容更新不要求切换应用 release。
8. 成员保存当前输入后重新打开/刷新页面；`LearningProvider` 在挂载时调用 `loadServerLearningContent`。确认桌面与手机安装新包、既有清单不变、已有旧卡排期一致，并在测试账号验证新卡评分、离线重开与恢复同步。管理员发布按钮只提示重新打开，不会推送重载所有已打开页面。

代码依据：`apps/server/src/content.ts:12–21,40–84`、`database.ts:38–45`；前端入口 `AccountTools.tsx:71–99`、`SettingsPage.tsx:86`；运行流程见 [部署手册](../server/deployment.md)、[实施合同](../server/implementation.md)、[内容审核记录](../server/content-review.md)。

## 5. 对成员当天清单、评分与离线内容的影响

### 5.1 每日安排与 3 张默认上限

`POST /plans/today` 先按账号和北京时间日期读取已存的 `dailyPlans`，找到就直接返回，之后才读当前内容。浏览器的本地计划仓储也先查旧清单，`saveServerPlan` 拒绝覆盖不同清单。追加卡片不会重排已固定日期的任务、修改该清单额度或重置完成证据。

不能笼统保证“新卡一律次日出现”：

| 情况 | 实际结果 |
| --- | --- |
| 发布前已生成当天清单 | 当天沿用原清单，新卡最早参加下一次新日期的选取 |
| 当天尚无清单，发布后首次生成 | 当天就按新学习包选取，可能选到新卡 |
| 主动打开卡片列表/概念页并加练 | 安装新包后当天即可练新增卡，不必等每日清单 |
| 离线且没有当天服务器清单 | 不在本地制造一份服务器计划；已有缓存内容仍可加练 |

“参加选取”不代表次日必定出现。`buildPersistentDailyPlan` 优先到期卡，再对未学卡按 ID 排序取名额；当前不会按四科轮流选新卡（四科轮流的是新题）。已有 80 张尚未学完、到期卡较多时，新卡可能继续等待。

默认 `DEFAULT_REVIEW_LIMITS={ questions:8, cards:10, newCards:3 }` 保持；实际新卡数为 `min(limits.newCards, limits.cards − 已选到期卡数)`。但 3 **不是全账号不可调的硬上限**：复习中心允许成员设置新卡额度，schema 允许 0–100 且不超过卡片总额度，保存后次日生效。自主加练也不受“每日新卡 3 张”限制，每轮最多 10 张、每卡最多两次额外重试。内容扩充不修改这些规则。

代码依据：`apps/server/src/sync.ts:214–233`；`packages/storage/src/learning-repository.ts:37–45,138–161`；`packages/domain/src/learning.ts:6,162–226`；`packages/storage/src/learning-schema.ts:28–47`；`ReviewPage.tsx:28–69,195–198`。

### 5.2 已有评分与进度

卡片间隔从不可变事件按 `cardId + cardVersion + 北京日期` 重放，同日取最低评分；每日选卡只用当天之前的事件。保留旧卡对象后，原 80 卡评分、间隔、到期日和个人暂停/覆盖不会因学习包 version 增长而清零。学习包安装事务只写内容库的 `learningPacks`，不写用户库的评分、作答、笔记或计划。题目进度按 `questionId + questionContentVersion` 绑定，未改变题面时继续沿用。

复习轮次保存完整卡片快照，评分使用该轮快照的卡版本。账号模式的轮次/评分和 outbox 同事务；服务端校验评分与轮次一致，不要求卡片仍出现在当前发布包中。因此旧轮次以及离线产生、稍后同步的合法评分不会因本次追加被当成无效记录删除。

个人编辑副本覆盖同 baseCardId 的公共卡，并保留个人版本；内容升级不会自动把成员个人编辑改回公共正文。概念四态是派生结果，新增当前卡会影响“所有当前卡都满足间隔”的证据条件，不能将显示状态变化解释为丢分。本批新增对象位于原无公共卡的 33 个概念，具体个人副本场景仍需兼容测试。

代码依据：`packages/domain/src/learning.ts:157–196`；`packages/storage/src/learning-repository.ts:20–28,164–200`；`packages/storage/src/index.ts:40` 与 `account-sync.ts:48–73`；`apps/server/src/sync.ts:48–50,76–80,107–120`；`apps/web/src/app/concept-register.ts:126–154`。

### 5.3 缓存、离线与更新时间

服务器目录/正文通过鉴权 API、`no-store` 获取。目录 version/digest 与本机一致时跳过正文；改变时抓取正文，校验包 ID、版本、摘要后才安装到 `408-content:<accountId>`。已有未同步评分在独立 `408-user:<accountId>`，不会被包替换或可再下载缓存清理触碰。学习包大小计入跨账号 250 MB 缓存预算；容量不足/安装失败应报错并保留原用户数据，不要求用户清库。

网络型 `TypeError` 且有合法已装包时可继续旧缓存；HTTP 错误、目录/正文不一致、解析错误等不会悄悄降级。离线资格仍是现有 7 天合同。纯离线成员继续使用已装的旧卡集，重新在线打开页面后才发现新版本。没有持续推送学习包的机制，普通学习记录同步不等于学习包已刷新。

跨日保持旧页面但服务器生成新清单时，清单可能引用本页尚未安装的新卡；UI 会将缺卡显示为不可用，联网重开安装即可，不应删清单重抽。发布验收需覆盖此不同步时点。

代码依据：`apps/web/src/app/server-learning.ts`、`LearningProvider.tsx:20–45,62–80`、`account-cache.ts:16–25,44–56`、`components/useDailyCardRound.ts:49–71`。

## 6. 内容回退及新卡评分的去向

### 6.1 用更高包版本恢复旧内容

保存上线前的旧包原文和规范摘要。若候选 `2026.11.25.1` 有问题，复制旧包内容，在确定性源上制作 `2026.11.25.2`（或高于所有已发版本的值），固定新的 createdAt，重新计算规范摘要并校验，然后仍走 preview → publish → 目录/正文回读。旧 80 卡的卡版本与对象保持原样；旧概念/映射与讲解恢复其原内容。版本更高的回退包可以只有原 80 张卡。

服务器拒绝降版，客户端 `DexieLearningContentRepository.install` 也拒绝降版及同版本不同摘要。直接把旧 JSON 改回文件、切回前一个应用 release、手改 `published` 或清浏览器库都不是完整内容回退方案。要使本地模式/Pages 也回退，需同步维护其生成源与新包版本；仅服务器发布不会改变 Pages。

本批无需数据库 schema 改动，常规回退不恢复数据库快照、不撤销成员会话、不重置 sync epoch。数据库恢复是另一个高风险流程：会丢失快照后的服务端记录，并触发重新登录/对账，不能用来回退几张卡片。

### 6.2 新评分保留，但当前包缺卡会停止自动排期

| 回退时状态 | 回退后的行为 |
| --- | --- |
| 新卡已有评分/完成轮次 | 事件和轮次快照保留，历史可读；当前包没有该卡时，不进入后续自动排期，也不计入当前概念卡证据 |
| 新卡轮次进行中或离线评分待同步 | 轮次自带新卡快照；现有代码仍可继续评分，合法轮次与事件可同步。回退不是强制撤销已经下发的卡片 |
| 当天固定清单包含被撤回的新卡 | 原清单不改写；已完成证据仍保留。尚未开始且当前缺卡的任务显示不可用，不自动补位。已有开放轮次可经历史入口继续 |
| 成员曾创建该新卡的个人副本 | 个人副本属于账号数据，原文与暂停状态保留；来源仍有效时可继续出现在个人卡列表/排期中 |
| 以后重新加入同 ID、同卡版本、同正文 | 原评分会重新参与该版本排期，间隔按原事件重放；不重新伪造评分 |
| 以后修正正文并提升该卡版本 | 旧版本评分保留为历史，不自动当作新版本已掌握；新版本需要自己的评分 |

因此，回退能阻止后续新清单选取被撤回的公共卡，但无法保证所有离线设备即时停止展示，也不能自动消除已有轮次中的错误正文。如果问题严重，需要组长安排内容说明及定向修订，不能靠删除成员记录解决。
